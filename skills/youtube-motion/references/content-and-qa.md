# 기획·출처·결과 화면·검수

## 자료 조사

- 새로운 주제는 공식 발표, 공식 도움말, 실제 제품 화면을 우선 확인한다. 검색 결과의 제목·요약만으로 기능을 확정하지 않는다.
- 발표일, 수정일, 조사일을 구분한다. “오늘 기준”이면 날짜와 시간대를 기록한다.
- 기능 지원 여부, 국가·플랜 제한, 가격, 출시 상태, 베타 여부 등 변할 수 있는 내용은 현재 공식 자료로 확인한다.
- 주장별 URL과 근거를 남긴다. 업체 자체 벤치마크를 객관적 직접 실험인 것처럼 옮기지 않는다.
- 원문은 사실 확인 자료로 사용하고, 긴 문장 그대로 낭독하는 대신 독자적인 설명과 활용 예를 만든다.
- 주제·사실을 바꾸지 않는 자막이나 호흡 수정에는 전체 웹조사를 다시 수행하지 않는다.
- 연결·자동화 지속성, 기기 지원, 실제 시험 범위가 핵심이면 [정밀 검수 기준](precision-checks.md)을 함께 적용한다. 공식 기능과 현재 구현을 구분한다.

## 시청자가 먼저 보아야 할 것

기본 편집 방향은 **유용한 AI 활용법과 구체적인 업무 수행**이다. 제품 이름·기능 수보다 어떤 입력을 넣어 어떤 작업물이 나오는지 보여준다. 공식 발표는 이 활용을 설명하는 근거로 연결한다.

| 업무 소재 | 보여줄 구체적인 결과 | 확인할 조건의 예 |
| --- | --- | --- |
| 회의 메모 정리 | 담당자·할 일이 채워진 후속 작업표 | 발언에 없는 마감일을 임의 확정하지 않음 |
| 자료 조사·보고서 | 출처가 연결된 비교표와 요약 | 최신 자료·원문 근거와 수치 확인 |
| 마케팅·콘텐츠 | 고객 질문에서 만든 초안과 수정 전후 | 실제 게시 전 내용·권리·계정 검토 |
| 표·반복 사무 | 입력 표와 수정 제안 또는 계산 결과 | 원본 보존, 계산·대상 행 확인 |
| 일정·생활 도구 | 실제 등록 또는 사용자가 확인할 초안 | 인증 지속성·권한·확인 동작·기기 시험 범위 |

위 항목은 새 주제를 기획할 때의 선택지다. 요청 없이 모두 제작하거나 자동 실행하지 않는다. 롱폼은 재현 가능한 과정과 조건을 설명하고, 숏폼은 하나의 결과와 핵심 입력을 독립적으로 전달한다.

기능을 세 가지 나열하는 대신 하나의 구체적인 변화가 보이게 한다.

| 약한 기획 | 더 구체적인 기획 방향 |
| --- | --- |
| “AI가 업무 효율을 높입니다” | 정리된 비교표를 먼저 보여주고, 어떤 자료를 넣어 어떤 항목을 뽑았는지 설명 |
| “마케팅, 사무, 크리에이터에 좋습니다” | 하나의 결과가 조사표 → 회의 자료 → 콘텐츠 초안으로 이어지는 실제 맥락 |
| 모든 칸이 “확인 필요”인 결과표 | 출처에 근거한 값 또는 “매출이 … 늘었다면”이라는 상황에 맞는 구체적인 수치 |
| “당신이 멈출 지점을 정하세요” | “메일은 보내기 전에 나한테 보여줘”처럼 사용자가 할 말 제시 |

- 후크는 낚시성 과장이 아니라 영상에서 실제로 보여줄 결과를 약속한다.
- 도입에는 **주체 + 발표·변화·가능해진 일**이 담긴 짧고 완결된 한 문장을 둔다. 첫 문장만 들어도 영상의 주제가 밝혀져야 한다. “오늘 …를 발표했어요”, “이제 …합니다”처럼 핵심 소식을 먼저 말하고, 다음 문장에서 그 의미를 쉬운 업무 상황으로 설명한다. 이 표현들은 선택 가능한 예시이며 고정 멘트가 아니다.
- “오늘”은 예정 발행일의 시간대와 실제 발표일을 대조해 맞을 때만 쓴다. 발행일이 미정이면 날짜를 단정하지 않는다. “이제”는 새로 가능해진 범위에만 쓰며, 발표·베타·단계적 적용을 전체 사용자 제공과 혼동하지 않는다.
- 첫 3초 안에 핵심 문구와 결과 일부를 읽을 수 있어야 한다. 화면 제목만 띄워 두고 음성은 활용 사례 중간부터 시작하지 않는다. 긴 타이핑 애니메이션 때문에 주장이 늦게 완성되지 않게 한다. 첫 문장을 억지로 빠르게 읽어 맞추지 말고 줄인다.
- 이후 입력·요청·진행·결과 차이를 단계적으로 보여준다. 화면 없는 기능 목록을 길게 설명하지 않는다.
- 실용 예시는 시청자가 따라 쓸 수 있는 입력 문장과 결과 필드를 포함한다.
- “10분 절약”, “성공률 100%”처럼 측정하지 않은 수치를 만들지 않는다. 추정이면 추정과 조건을 분명히 밝힌다.
- 사용자 검토가 필요한 행동은 구체적으로 말한다. “예약은 내가 확인하고 할게”, “메일 초안만 만들어줘”처럼 실제 요청 형태를 사용한다.

## 숏츠: 한 질문·한 핵심

**한 편에 한 가지 질문만 다루고, 본 후에 핵심 내용이 하나 남아야 한다.** 기획할 때 질문과 답을 각각 한 문장으로 적는다. 그 답을 설명하지 않는 기능·비교·조건은 빼거나 다른 편으로 나눈다. 선택에 꼭 필요한 조건은 해당 내용 옆에서 짧게 말한다.

| 순서 | 전달할 내용 | 판단 기준 |
| --- | --- | --- |
| 3초 훅 | 두괄식 핵심 변화·이익과 결과 화면 | 3초만 봐도 무엇이 쓸모 있는지 안다. 모호한 질문이나 긴 인사로 시작하지 않는다. |
| 쉬운 비유나 업무 상황 | 익숙한 입력 → 필요한 결과 | 회의 메모 → 보고서 → 발표자료처럼 한 상황으로 설명한다. 비유가 따로 설명을 요구하면 쓰지 않는다. |
| 핵심 차이 | 왜 편한지, 무엇이 다른지 | 제품명·전문 용어·중요한 조건은 정확히 유지하되 쉬운 말로 곧바로 푼다. 성능 우열을 추측하지 않는다. |
| 바로 쓸 한 문장 | 실제 요청문 또는 구체적인 행동·선택 기준 | “같은 내용으로 발표자료 5장도 만들어줘”처럼 영상 밖에서 바로 써먹을 수 있다. |

- 첫 3초는 낚시가 아니라 뒤에서 보여줄 결과에 대한 약속이다. 말과 화면이 함께 핵심을 전달해야 한다. 자막 전체를 읽기도 전에 넘어가거나 속도를 억지로 올려 맞추지 않는다.
- **“TOP 3”, “이것만 기억하세요”는 사용자가 든 예시다. 필수 문구·기본 형식·매 편의 마무리로 고정하지 않는다.** 목록형이 주제에 맞으면 쓸 수 있지만, 한 질문에 답하는 여러 표현 기법 중 하나로 취급한다. 서로 다른 세 주제를 한 영상에 끼워 넣지 않는다.
- 끝의 핵심은 앞의 훅을 회수한다. 막연한 감탄·구독 요청만 남기지 않는다. ‘한 대화에서 다음 결과물을 이어서 요청한다’처럼 한 문장으로 기억되어야 한다.
- 업데이트를 설명할 때는 **무엇이 바뀌었는지 → 하던 일을 어떻게 이어갈 수 있는지 → 어떤 수고가 줄어드는지**를 연결한다. 탭·기능이 합쳐졌다는 사실만으로 편리함을 설명했다고 판단하지 않는다. 이전에도 가능했던 일을 새 기능처럼 말하지 않고, 선택·자료 이동·반복 설명 등 실제 달라진 작업 과정을 짚는다.
- 바로 쓸 요청문을 보여준 뒤 효용으로 끝맺어도 된다. “이 보고서로 발표자료 다섯 장도 만들어줘” 다음에 “앞서 정리한 내용을 이어 쓰니까 자료를 옮기며 같은 설명을 반복하는 수고가 줄어요”처럼 앞의 상황에서 생기는 이점을 말한다. 요청문이 반드시 영상의 마지막 문장이어야 하는 것은 아니다. 다른 주제에는 그 작업에서 줄어드는 수고나 가능해진 결과를 쓴다.
- 마지막 문장은 앞의 결과와 인과관계가 이어져야 한다. 새 기능이나 새 사례를 끝에서 꺼내지 않는다. 효과를 설명할 때 측정하지 않은 시간 절약이나 완전 자동화를 덧붙이지 않는다. 음성의 마무리와 결과 유지 시간은 [숏폼 마무리](voice-and-rhythm.md#숏폼-마무리)를 따른다.
- 이 형식이 강사식 말투를 허용하는 것은 아니다. “이것만 기억하세요” 뒤에는 곧바로 구체적인 핵심을 붙이고, “오늘 배우실 내용”, “이해를 돕기 위한 예시” 같은 제작자 안내는 넣지 않는다.

## 숏폼 기법 선택과 스토리보드

### 제작 시점에 확인하고 주제에 맞게 선택

- 새 기획 때 최근 실제 Shorts·Reels 사례와 플랫폼의 제작 자료를 웹에서 확인한다. 주제·대상 시청자·정보 전달 방식이 유사한 사례를 우선하고, 확인한 URL과 게시일·확인일을 기획 기록에 남긴다.
- 기억에 있는 기법을 곧바로 “요즘 인기”라고 부르지 않는다. 인기·상승 추세를 주장하려면 이를 뒷받침하는 최근 자료를 확인한다. 확인할 수 없으면 일반적으로 쓰이는 기법과 최신 사례를 구분한다. 한 영상의 조회 수만으로 특정 편집법의 효과나 재현 가능한 성과를 단정하지 않는다.
- 선택 기준은 주제의 핵심을 얼마나 빨리 이해시키는지, 시청자가 어떤 결과를 궁금해할지, 실제 근거·화면으로 끝까지 답할 수 있는지다. 짧은 컷·큰 자막·유행 음원만 붙이는 것을 기획으로 대신하지 않는다.
- 하나의 주된 기법을 고르고 필요한 보조 기법만 더한다. 아래는 선택 가능한 예시이며 최신 인기 순위나 의무 목록이 아니다. 최근 확인한 다른 기법이 더 맞으면 사용한다.

| 기법 예시 | 잘 맞는 주제 | 적용 방향 |
| --- | --- | --- |
| 결과 먼저 공개 | 문서·디자인·자동화 결과처럼 눈에 보이는 변화 | 완성 결과를 첫 장면에 놓고 어떤 요청으로 이어지는지 설명 |
| 전후 비교 | 업데이트로 작업 과정이 바뀌는 주제 | 같은 업무의 바뀐 전후를 나란히 보여주고 달라진 한 지점을 강조 |
| 흔한 오해 바로잡기 | 이름·탭 변경이 기능 삭제 등으로 오해되는 주제 | 첫 문장에서 정확한 사실을 말하고 실제 달라진 점과 근거를 제시 |
| 익숙한 업무 상황의 짧은 이야기 | 추상적인 기능을 실용적으로 설명해야 하는 주제 | 회의 직전·보고서 수정처럼 익숙한 문제를 한 요청과 결과로 연결 |
| 같은 조건에서 선택 비교 | 서비스·기능을 고르는 주제 | 동일한 입력·조건으로 차이를 설명하고 시청자가 쓸 판단 기준으로 끝냄 |
| 실수 하나와 고치는 방법 | 설정·조건을 놓치기 쉬운 활용법 | 실제 흔한 실수를 짚고 바로 바꿀 요청·설정 하나를 보여줌 |
| 단계별 발견·다음 결과에 대한 궁금증 | 과정에 의미 있는 변화가 있는 주제 | 핵심 이익은 먼저 밝히고 다음 결과를 궁금하게 만든 뒤 영상 안에서 답함 |
| 짧은 목록·체크리스트 | 한 결정에 복수의 기준이 필요한 주제 | 개수보다 선택 기준이 핵심이 되도록 구성; TOP 3는 필요할 때만 사용 |

첫 3초 훅, 쉬운 상황, 핵심 차이, 바로 쓸 문장의 역할은 유지한다. 선택한 기법은 이 흐름을 전달하는 방식이며, 매번 같은 대사와 장면 틀로 찍어내라는 뜻이 아니다. 다음 장면이 궁금하게 만들되 결론을 숨기거나 근거 없는 충격·불안·시간 절약 수치를 만들지 않는다.

### 사용자에게 보여줄 스토리보드

먼저 “이 주제에는 어떤 기법이 왜 맞고, 어떤 상황과 화면으로 풀어갈지”를 설명한다. 기법 이름만 나열하지 말고 **이번 주제의 구체적인 적용**을 적는다. 최근 참고한 사례와 적용한 부분은 짧게 연결하되 문구·화면을 그대로 복제하지 않는다.

| 예상 구간 | 화면·구도 | 실제 나레이션 | 핵심 화면 문구 | 모션·다음 장면 연결 | 전달할 사실·근거 |
| --- | --- | --- | --- | --- | --- |
| 0–3초 훅 | 첫 프레임부터 보일 주체·변화·결과 | 주체와 무슨 소식인지 함께 밝히는 완결된 도입 한 문장 | 휴대폰에서도 바로 읽힐 핵심 | 문장을 가리지 않고 변화가 보이는 움직임 | 훅이 약속한 사실과 시점 |
| 상황·차이·마무리 | 의미 단위별로 행을 나눠 작성 | 요지 대신 검토 가능한 실제 문장 | 화면에 들어갈 문구 | 읽는 시간과 변화의 이유 | 출처·필수 조건 |

- 최종 초 수는 TTS 전에 확정하지 않고 예상 구간으로 표시한다.
- 각 편의 질문 하나, 남길 핵심 하나, 마지막에 바로 쓸 문장을 스토리보드와 함께 제시한다.
- 기법 설명·제작 판단·출처 메모는 기획 문서에만 둔다. 영상의 나레이션·자막에 강사 메모를 넣지 않는다.
- 스토리보드 원고를 `humanize-korean`으로 윤문하고 사실·조건을 다시 대조한 뒤 사용자에게 보여준다.
- **사용자가 이 스토리보드를 승인한 뒤 제작한다.** 시작 요청은 조사와 기획을 허용한다. 승인 전에는 음성 생성, 제작용 영상 코드·자산 생성, 모션 제작, 렌더를 하지 않는다. 기획안 버전과 승인 여부를 상태 파일에 기록한다. 사용자의 수정 의견은 기획안을 고치라는 뜻이며, 제작 승인으로 자동 해석하지 않는다.

## 롱폼 구성과 흐름: 사용자 피드백으로 정한 기준

2026-10-01 dot 사용법 편에서 사용자가 직접 요청한 기준이다. 새 롱폼을 기획하고 검수할 때 적용한다.

- **맨 앞에 하이라이트를 먼저 보여준다.** 뒤에 나올 가장 놀라운 결과 장면 서너 개를 10초 안팎으로 빠르게 이어 붙이고, 그 뒤에 본 영상을 시작한다. 하이라이트의 첫 문장에도 주체(예: 챗GPT)를 넣어 무슨 이야기인지 알 수 있게 한다. 하이라이트에 쓴 장면은 본편에서 다시 풀어 준다.
- **기존에 쓰던 것과 무엇이 다른지 초반에 말한다.** 새 제품·기능을 소개하면 "그냥 ○○랑 뭐가 다른가"에 답하는 장면을 도입 바로 뒤에 둔다. 기존 방식은 여기까지, 새 것은 이 점이 다르다는 식으로 차이를 두세 가지로 좁힌다. 기존 방식으로도 되는 일을 새 기능만 되는 것처럼 말하지 않는다. 차이는 "맡겨 놓고 내 할 일 하러 간다"처럼 시청자가 얻는 편함으로 끝맺는다.
- **초반에 말한 차이를 뒤에서 하나씩 회수한다.** 시연이 끝난 뒤 "여기까지 맡긴 일이 여섯 가지, 전부 대화창 하나에서"처럼 실제로 한 일을 세어 처음의 차이와 연결한다. 장면 제목에도 어느 차이를 보여 주는지 표시한다.
- **흐름과 맥락을 따로 검수한다.** 렌더 전에 원고를 처음부터 이어 읽으며 앞 장면과 연결되지 않고 튀는 장면이 없는지 본다. 끊기는 곳에는 "세 번째 차이는 만든 날 바로 봤어요"처럼 앞을 받는 문장을 넣는다. 시간 순서가 뒤바뀌는 장면은 그 사실을 문장으로 밝힌다.
- **왜 유용한지를 실제 화면의 한 순간으로 보여준다.** "개인 비서 같다"는 말은 닷이 먼저 "어느 쪽부터 도와드릴까요?"라고 묻는 실제 메시지처럼 구체적인 장면에 붙인다. 개인 정보가 있으면 본문을 블러하고 요지를 표지로 얹는다.
- **읽기만 하는지, 직접 실행하는지를 구분해 말한다.** 조건이 붙은 제한(먼저 살펴볼 때는 읽기 전용)을 제품 전체의 한계처럼 말하지 않는다. 요청하면 직접 하는 일(메일 작성, 일정 입력, 문서 생성·수정)도 함께 말한다. 직접 실행해 확인한 것과 공식 글·사용자 경험에 근거한 것을 검토 자료에 구분해 적는다.
- **"기대해 본다"는 마무리에는 아직 안 되는 일을 쓴다.** 이미 되는 기능을 앞으로의 기대처럼 말하지 않는다. 공식 글이 밝힌 다음 계획이나 로드맵을 근거로 삼는다.
- **"~만", "~때만", "전부" 같은 한정 표현은 원문과 대조한다.** 원문이 "A는 포함되지 않는다, B는 포함된다"라고만 썼으면 "B일 때만 포함된다"로 바꿔 쓰지 않는다. 사용 한도·요금·제공 범위 문장은 원문 표현 그대로 옮긴다.
- **단정하는 도입 대신 본 사람의 말로 쓴다.** "이 한 줄이면 돼요"보다 "저는 이게 가장 눈이 갔어요"처럼 말한다.
- **어미를 섞는다.** "~했어요"가 세 문장 넘게 이어지지 않게 "~거든요, ~더라고요, ~죠, ~네요, ~고요"를 섞고, "와/과"보다 "랑/이랑", "확인하지 못한"보다 "확인이 안 되는"처럼 입말을 쓴다. 같은 어미를 영상 전체에서 네 번 넘게 반복하지 않는다.
- **썸네일에 최신성을 보인다.** 발표·행사에서 나온 기능이면 "DevDay 2026 NEW"처럼 행사 이름과 새 기능이라는 표시를 넣는다. 설명란은 핵심 차이, 챕터, 알아 둘 조건, 공식 링크만 짧게 적는다.

## 강의가 아닌 활용 사례의 말투

완성한 도구나 결과를 보여주며 **“이런 방법도 있다”**고 소개한다. 시청자를 수강생으로 대하거나 한 문장 입력만으로 완성·성공·지속적인 자동화를 보장하지 않는다.

| 피할 표현 | 권장하는 방향 |
| --- | --- |
| “휴대폰용 앱을 만들어줘, 라고 요청해서 만드는 겁니다” | “말로 일정을 정리하는 도구를 만들어 달라고 요청해 볼 수 있어요.” 이후 실제 확인·수정 과정을 함께 보여줌 |
| “이렇게 하면 완성됩니다”, “말만 하면 됩니다” | “이런 방식으로 시작해 볼 수도 있어요”, “필요한 부분을 확인하며 고쳐봤어요” |
| “이 시연 앱은”, “실습용 앱에서는” | 맥락에 맞는 “이 도구는”, “여기서는”, “지금 보이는 화면에서는” |
| “따라 해보세요”, “지금부터 배워보겠습니다” | 입력·결과를 바로 보여주며 무엇을 해봤는지 설명 |
| “기본 흐름은 이것입니다”라는 일반론 | 이번 사례에서 어떤 부분을 확인하고 바꿨는지 구체적으로 설명 |

- 요청 문장을 인용하는 것 자체는 가능하다. 그 문구와 완성 결과를 곧바로 이어 붙여 한 번에 완성됐다고 오해하게 하지 않는다. 필요한 연결 설정·검토·수정은 내용에 맞게 드러낸다.
- “해봤어요”, “확인했어요”는 실제 실행 근거가 있을 때만 쓴다. 실행하지 않은 상황은 “금요일 회의가 잡혔다면”, “매출이 … 늘었다면”처럼 이야기 안에서 조건으로 표현한다.
- 확인된 결과까지 전부 “아마”, “일 수도”로 흐리지 않는다. 사용 가능성을 단정하지 않는 것과 중요한 제한 조건을 누락하는 것은 다르다.
- “설명용 예시”, “가상 예시”, “가상 데이터”, “공식 기능 안내를 바탕으로 재구성”, “업무 활용 제안”, “시연”, “실습”, “강의”, “데모” 같은 제작자·강사의 표찰과 메타 멘트는 시청자용 원고·화면·자막에서 금지한다. 자료의 성격과 제작 경위는 내부 검토 기록에 남긴다.
- 억지 비유로 제품을 설명하지 않는다. 비교 대상 사이의 관계가 즉시 이해되고 실제 기능의 의미를 보존할 때만 짧게 사용한다. “상담실과 작업실 사이의 벽을 없앴다”는 사용자가 기각했다. 실제로 흔한 요청·결정·수정 상황을 우선한다.
- 영상 하단 날짜와 제작용 장면·페이지 번호를 넣지 않는다. 발표일처럼 내용 자체에 필요한 날짜는 해당 사실을 설명하는 장면에서 사용할 수 있다.
- 원고뿐 아니라 제목·화면 문구·캡처 안의 제작자 메모·자막도 확인한다. 실제 UI의 문구를 바꾸어 증거를 왜곡하지 말고, 불필요한 메모는 핵심 결과를 훼손하지 않는 범위에서 잘라낸다.
- 이 말투는 스타일 1·2, 롱폼·숏폼에 공통 적용한다.

## 화면의 세 가지 자료 종류

| 종류 | 표현 |
| --- | --- |
| 공식 사이트·제품 소개 캡처 | 필요한 원문·브랜드를 정확하게 보여주고 출처·수집일은 검토 기록에 보존 |
| 직접 실행해 검증한 결과 | 실제 입력·결과·조건을 보존; 확인한 범위 안에서만 설명 |
| 직접 구성한 업무 상황 | 조건형 문장과 내용이 채워진 도표·문서로 설명. 실제 제품 실행 화면·실측 결과처럼 꾸미지 않음. 제작 경위는 내부 기록에 보존 |

공식 사이트의 화면을 캡처했다고 직접 테스트한 것이 아니다. 직접 구성한 문서·수치를 제품이 생성한 결과처럼 연출하지 않는다. 가정한 업무 상황은 구체적인 조건으로 설명하고, 실제 제품 UI가 필요하면 정확한 캡처를 사용한다. 실제 실행이 필수인 요청이라면 그 제약을 사용자에게 알려야 한다.

## humanize-korean 필수 윤문

1. 내용과 구조를 먼저 확정한다. 첫 3초 훅, 한 질문·한 핵심, 업무 상황, 마지막에 바로 쓸 문장까지 정한 뒤 팩트를 확인한다. 구조 변경과 새 주장 추가를 윤문 스킬에 떠넘기지 않는다.
2. 현재 스킬 목록의 `humanize-korean/SKILL.md`를 읽고 그 절차와 룰북을 적용한다. 사용자 지정 경로가 있으면 우선한다. 목록에 없으면 `$CODEX_HOME/skills/humanize-korean/SKILL.md` 또는 기본 사용자 폴더의 `.codex/skills/humanize-korean/SKILL.md`를 확인한다. 없으면 다른 설치 위치를 찾고, 끝내 찾지 못하면 ‘필수 윤문 미실행’이라고 알린다. 적용했다고 표시하지 않는다.
3. 장르는 말로 듣는 한국어 정보 영상으로 유지한다. 번역투·추상 명사·불필요한 접속사·강사 말투를 다듬되, 수치·날짜·제품명·인용·가능 조건은 보존한다. 윤문 단계에서 새 비유나 과장을 만들지 않는다. 이미 자연스러우면 검토 결과를 남기고 유지한다.
4. 원문과 윤문본, 변경 요약과 자체검증을 에피소드 기록에 연결한다. `production-status.json` 등에 적용한 스킬 위치와 최종 원고 경로를 기록하고, 윤문본이 실제 음성·자막 원고인지 확인한다. 로컬 경로를 배포용 스킬 안에 고정하지 않는다.
5. 윤문 뒤 사실과 조건을 다시 대조한 다음 음성을 만든다. 제작 중 문구가 바뀌면 바뀐 구간에 다시 적용하고 그 구간의 음성·자막·모션을 맞춘다. 수정하지 않은 음성은 보존한다.

## 기획안의 최소 구성

새 기획 승인을 위한 문서는 아래 항목을 구체적으로 채운다.

- 제목 후보, 시청자 문제, 영상에서 보여줄 한 가지 핵심 변화.
- 길이와 편수: 사용자 요청 우선. 정확한 최종 초 수를 음성 생성 전에 사실처럼 확정하지 않음.
- 스타일 1(화면 중심) 또는 스타일 2(일러스트 중심), 그리고 별도의 팔레트 번호. 스타일을 선택한다고 두 버전을 모두 제작하는 것으로 해석하지 않음.
- 선택한 숏폼 기법, 이 주제에 맞는 이유, 구체적인 적용 방식, 최근 확인한 참고 사례와 출처.
- 첫 3초 후크의 실제 문장과 화면.
- 장면 표: 예상 구간 / 화면·구도 / 실제 나레이션 / 핵심 화면 문구 / 모션·연결 / 자료 종류·출처. 위 스토리보드 형식을 활용한다.
- 시각 구성: 주 소재(실제 화면·일러스트·픽토그램·큰 글자 등), 구도, 움직임이 설명할 변화, 읽는 구간, 다음 장면으로 이어지는 대상. 동일한 틀이 연속되면 이유를 확인하고 필요할 때 구성을 바꿈.
- 각 숏폼의 질문 하나, 핵심 한 문장, 첫 3초의 말·화면, 업무 상황, 핵심 차이, 끝에서 바로 쓸 문장. 롱폼을 잘라 붙이는 계획으로 대체하지 않음.
- 실제로 확인한 사항과 예시로 설명할 사항, 필요한 제한 조건.

사용자에게 스토리보드를 전달한 뒤 승인 응답을 기다린다. 승인 전까지 상태는 `awaiting_storyboard_approval`이다. 사용자 승인 후 같은 기획의 제작·렌더에 재승인을 요구하지 않는다. 새로운 훅·이야기 구조·핵심 주장·범위로 재기획할 때는 변경 스토리보드에 대한 승인을 먼저 받는다. 기존 승인 범위의 오탈자·자막·모션·호흡 수정은 바로 진행한다.

## 최종 검수

요청 범위에 맞는 검수만 수행한다. 전체 본편을 새로 제작했다면 전체를 검수하고, 특정 수정이라면 변경 구간과 파급 범위를 확인한다.

### 콘텐츠·시각

- 첫 3초의 주장과 화면이 일치하며 읽을 수 있는가?

- 기능 설명마다 시청자가 볼 수 있는 구체적인 결과가 있는가?
- 공식 자료·직접 실행·직접 구성한 상황의 범위를 정확하게 설명하고 내부 근거를 보존했는가?
- 숏츠를 본 후 남을 핵심을 한 문장으로 말할 수 있는가? 한 질문에 답하며 마지막 문장을 실제 요청이나 판단에 쓸 수 있는가?
- 일상·업무 상황이 즉시 이해되는가? 억지 비유와 불필요한 전문 용어 나열은 없는가?
- 시청자가 “그래서 내 일이 어떻게 편해지나?”에 한 문장으로 답할 수 있는가? 마지막 효용이 앞서 보여준 작업과 연결되는가?
- 작업물 안의 문구가 앞 장면에서 충분히 소개됐는가? 서로 다른 카드에 같은 글을 넣었다면, 무엇을 이어 쓰는지와 결과물의 차이가 별도 해설 없이 보이는가?
- 강사 메모·메타 멘트·하단 날짜·제작용 페이지 번호가 없는가?
- `humanize-korean` 윤문과 의미 보존 검토를 완료했고, 검토한 원고가 실제 음성·자막에 반영됐는가?
- 자막 줄바꿈이 자연스럽고, 행간·자간·화면 가장자리 여백이 답답하지 않은가?
- 밝은/어두운 배경의 배색과 승인 HEX가 맞는가?
- 서비스·제품의 공식 로고를 관련 장면과 썸네일에 사용했는가? 대상 제품이 맞고 형태·비율·색이 원본과 일치하는가?
- 글자가 먼저 나온 후 밑줄·화살표·동그라미가 정확한 대상을 강조하는가?
- 캐릭터와 모션이 설명을 돕고, 읽기 시간을 침범하지 않는가?
- 선택한 스타일이 반영되었는가? 스타일 1은 실제 화면·타이포의 위계와 의미 있는 변화가 보이는가? 스타일 2는 작은 아이콘 추가에 그치지 않고 큰 그림의 움직임이 설명을 맡는가?
- 비교·과정·결과 장면이 서로 다른 크기 관계와 구도를 가지는가? 똑같은 박스 등장과 페이드 전환이 반복되지 않는가?
- 전환 중 공통 대상이나 시선의 위치가 이어지고, 핵심 문장이 잘리지 않는가?
- 세로 화면에서 제품 UI, 결과와 자막이 플랫폼 버튼 영역에 가리지 않는가?

### 오디오·동기화

- 음성 트랙이 실제로 들어 있고 승인된 목소리를 사용하는가?
- 발화 속도는 유지되고 롱폼의 의미 경계에 적절한 쉼이 있는가?
- 쉼 구간에 다음 장면·자막이 먼저 진행하지 않는가?
- 실제 발화와 자막·강조 효과가 맞는가?
- 음성 잘림·클리핑·갑작스러운 음량 변화·의도하지 않은 중복 발화가 없는가?
- 호흡 수정 중 피치·채널 구성·음량이 바뀌지 않았는가?

청취 도구가 있으면 대표 구간을 직접 확인한다. 청취하지 못했을 때 수치 검사만으로 자연스럽게 들린다고 단정하지 않는다.

### 파일

- 출력 파일의 길이·해상도·프레임레이트·영상/음성 코덱을 확인하고 전체 디코딩 오류를 검사한다.
- 설명 없이 무음이거나 검은 프레임인 구간이 없는지 확인한다. 의도된 쉼과 배경을 오류로 오인하지 않는다.
- 최종 SRT의 시작·끝·순서·영상 종료 범위를 검증한다.
- 속도나 쉼을 바꿨으면 최신 타임라인에서 SRT와 검토 자료를 다시 만든다.
- 수정 대상 밖의 승인본이 유지되었는지 확인한다.

기본 출력 예: 가로 1920×1080, 세로 1080×1920, 30fps, H.264/AAC MP4. 현재 프로젝트와 사용자 요청이 있으면 우선한다. 특정 LUFS 수치를 맞추려고 이미 승인된 음량을 임의로 바꾸지 않는다.

## 전달과 발행

- MP4, 별도 SRT, 간결한 원고·출처·예시 구분 자료를 전달한다. 대규모 문서 묶음이 아니라 실제 검토에 필요한 자료를 만든다.
- 수정된 숏츠는 각 편의 인라인 미리보기와 개별 MP4 링크를 먼저 제공한다. 파일명·길이로 구별하고 ZIP만 던져두지 않는다.
- 제작·기술 검수 완료, 사용자 검토 대기, 발행 완료 상태를 구분한다.
- 사용자가 완성 영상을 승인하면 **제목·설명·썸네일을 제작하고 YouTube 업로드까지 진행한다.** 이 후속 작업은 사용자가 위임한 기본 흐름이다. 상세 기준은 [승인 후 YouTube 업로드](youtube-upload.md)를 따른다.
- 기획·제작 승인을 완성 영상 승인으로 혼동하지 않는다. 승인한 영상 버전과 대상 채널을 확인하고, 공개·예약 설정은 사용자가 정한 범위를 따른다. 이미 받은 권한은 다시 묻지 않는다.
