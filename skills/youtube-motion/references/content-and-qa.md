# 기획·출처·결과 화면·검수

## 자료 조사

- 새로운 주제는 공식 발표, 공식 도움말, 실제 제품 화면을 우선 확인한다. 검색 결과의 제목·요약만으로 기능을 확정하지 않는다.
- 발표일, 수정일, 조사일을 구분한다. “오늘 기준”이면 날짜와 시간대를 기록한다.
- 기능 지원 여부, 국가·플랜 제한, 가격, 출시 상태, 베타 여부 등 변할 수 있는 내용은 현재 공식 자료로 확인한다.
- 주장별 URL과 근거를 남긴다. 업체 자체 벤치마크를 객관적 직접 실험인 것처럼 옮기지 않는다.
- 원문은 사실 확인 자료로 사용하고, 긴 문장 그대로 낭독하는 대신 독자적인 설명과 활용 예를 만든다.
- 주제·사실을 바꾸지 않는 자막이나 호흡 수정에는 전체 웹조사를 다시 수행하지 않는다.
- 연결·자동화 지속성, 기기 지원, 실제 시험 범위가 핵심이면 [정밀 검수 기준](precision-checks.md)을 함께 적용한다. 공식 기능과 현재 구현을 구분한다.

- 공식 근거와 직접 실행 관찰의 표현 강도는 [정밀 검수 기준](precision-checks.md#사실을-표현하는-강도)을 따른다. 서비스 비교는 "이번에 스킬에 담긴 것"처럼 관찰한 사실로 말하고, 품질 우열은 체감과 변동 가능성을 함께 말한다.
- 비교할 서비스는 같은 입력·같은 요청으로 직접 실행하고, 화면 캡처와 결과물을 검증 기록에 남긴다. 결과가 그때그때 다른 기능은 "복불복에 맡기기보다 원하는 걸 프롬프트에 분명하게 적기" 같은 실용 조언으로 마무리한다.

## 시청자가 먼저 보아야 할 것

기본 편집 방향은 **유용한 AI 활용법과 구체적인 업무 수행**이다. 제품 이름·기능 수보다 어떤 입력을 넣어 어떤 작업물이 나오는지 보여준다. 공식 발표는 이 활용을 설명하는 근거로 연결한다.

| 업무 소재 | 보여줄 구체적인 결과 | 확인할 조건의 예 |
| --- | --- | --- |
| 회의 메모 정리 | 담당자·할 일이 채워진 후속 작업표 | 발언에 없는 마감일을 임의 확정하지 않음 |
| 자료 조사·보고서 | 출처가 연결된 비교표와 요약 | 최신 자료·원문 근거와 수치 확인 |
| 마케팅·콘텐츠 | 고객 질문에서 만든 초안과 수정 전후 | 실제 게시 전 내용·권리·계정 검토 |
| 표·반복 사무 | 입력 표와 수정 제안 또는 계산 결과 | 원본 보존, 계산·대상 행 확인 |
| 일정·생활 도구 | 실제 등록 또는 사용자가 확인할 초안 | 인증 지속성·권한·확인 동작·기기 시험 범위 |

위 항목은 새 주제를 기획할 때의 선택지다. 요청 없이 모두 제작하거나 자동 실행하지 않는다. 롱폼은 재현 가능한 과정과 조건을 설명하고, 숏폼은 하나의 결과와 핵심 입력을 독립적으로 전달한다.

기능을 세 가지 나열하는 대신 하나의 구체적인 변화가 보이게 한다.

| 약한 기획 | 더 구체적인 기획 방향 |
| --- | --- |
| “AI가 업무 효율을 높입니다” | 정리된 비교표를 먼저 보여주고, 어떤 자료를 넣어 어떤 항목을 뽑았는지 설명 |
| “마케팅, 사무, 크리에이터에 좋습니다” | 하나의 결과가 조사표 → 회의 자료 → 콘텐츠 초안으로 이어지는 실제 맥락 |
| 모든 칸이 “확인 필요”인 결과표 | 출처에 근거한 값 또는 명확히 가상이라고 표시한 구체적인 예시 값 |
| “당신이 멈출 지점을 정하세요” | “메일은 보내기 전에 나한테 보여줘”처럼 사용자가 할 말 제시 |

- 후크는 낚시성 과장이 아니라 영상에서 실제로 보여줄 결과를 약속한다.
- 첫 3초 안에 핵심 문구와 결과 일부를 읽을 수 있어야 한다. 긴 타이핑 애니메이션 때문에 주장이 늦게 완성되지 않게 한다.
- 이후 입력·요청·진행·결과 차이를 단계적으로 보여준다. 화면 없는 기능 목록을 길게 설명하지 않는다.
- 실용 예시는 시청자가 따라 쓸 수 있는 입력 문장과 결과 필드를 포함한다.
- “10분 절약”, “성공률 100%”처럼 측정하지 않은 수치를 만들지 않는다. 추정이면 추정과 조건을 분명히 밝힌다.
- 사용자 검토가 필요한 행동은 구체적으로 말한다. “예약은 내가 확인하고 할게”, “메일 초안만 만들어줘”처럼 실제 요청 형태를 사용한다.

## 강의가 아닌 활용 사례의 말투

완성한 도구나 결과를 보여주며 **“이런 방법도 있다”**고 소개한다. 시청자를 수강생으로 대하거나 한 문장 입력만으로 완성·성공·지속적인 자동화를 보장하지 않는다.

| 피할 표현 | 권장하는 방향 |
| --- | --- |
| “휴대폰용 앱을 만들어줘, 라고 요청해서 만드는 겁니다” | “말로 일정을 정리하는 도구를 만들어 달라고 요청해 볼 수 있어요.” 이후 실제 확인·수정 과정을 함께 보여줌 |
| “이렇게 하면 완성됩니다”, “말만 하면 됩니다” | “이런 방식으로 시작해 볼 수도 있어요”, “필요한 부분을 확인하며 고쳐봤어요” |
| “이 시연 앱은”, “실습용 앱에서는” | 맥락에 맞는 “이 도구는”, “여기서는”, “지금 보이는 화면에서는” |
| “따라 해보세요”, “지금부터 배워보겠습니다” | 입력·결과를 바로 보여주며 무엇을 해봤는지 설명 |
| “기본 흐름은 이것입니다”라는 일반론 | 이번 사례에서 어떤 부분을 확인하고 바꿨는지 구체적으로 설명 |

- 요청 문장을 인용하는 것 자체는 가능하다. 그 문구와 완성 결과를 곧바로 이어 붙여 한 번에 완성됐다고 오해하게 하지 않는다. 필요한 연결 설정·검토·수정은 내용에 맞게 드러낸다.
- “해봤어요”, “확인했어요”는 실제 실행 근거가 있을 때만 쓴다. 실행하지 않은 제안은 “해볼 수 있어요”, 설명용 화면은 “예시”로 구분한다.
- 확인된 결과까지 전부 “아마”, “일 수도”로 흐리지 않는다. 사용 가능성을 단정하지 않는 것과 중요한 제한 조건을 누락하는 것은 다르다.
- “시연”, “실습”, “강의”, “데모” 같은 제작자·강사의 표찰은 시청자용 원고·화면·자막에서 피한다. 자료 성격에 필요한 “예시”, “실제 화면 일부”, “설명 일러스트” 표시는 유지한다.
- 원고뿐 아니라 제목·화면 문구·캡처 안의 제작자 메모·자막도 확인한다. 실제 UI의 문구를 바꾸어 증거를 왜곡하지 말고, 불필요한 메모는 핵심 결과를 훼손하지 않는 범위에서 잘라낸다.
- 이 말투는 스타일 1·2, 롱폼·숏폼에 공통 적용한다.

## 화면의 세 가지 자료 종류

| 종류 | 표현 |
| --- | --- |
| 공식 사이트·제품 소개 캡처 | 공식 소개 화면이라는 맥락, 출처·수집일 기록 |
| 직접 실행해 검증한 결과 | 실제 입력·결과·조건을 보존; 확인한 범위 안에서만 설명 |
| 직접 만든 설명용 예시 | 화면에 “설명용 예시”, “가상 데이터” 등 명확한 표시 |

공식 사이트에 있는 데모를 캡처했다고 직접 테스트한 것이 아니다. 설명용 예시를 제품이 생성한 결과처럼 연출하지 않는다. 결과가 필요하지만 실제 실행이 불가능하면, 이미 승인된 범위 안에서 구체적인 예시를 만들고 그 성격을 표시한다. 실제 실행이 필수인 요청이라면 제약을 알려야 한다.

## 기획안의 최소 구성

새 기획 승인을 위한 문서는 아래 항목을 구체적으로 채운다.

- 제목 후보, 시청자 문제, 영상에서 보여줄 한 가지 핵심 변화.
- 길이와 편수: 사용자 요청 우선. 정확한 최종 초 수를 음성 생성 전에 사실처럼 확정하지 않음.
- 스타일 1(화면 중심) 또는 스타일 2(일러스트 중심), 그리고 별도의 팔레트 번호. 스타일을 선택한다고 두 버전을 모두 제작하는 것으로 해석하지 않음.
- 첫 3초 후크의 문구와 화면.
- 장면 표: 의미 단위 / 화면에 보일 결과 / 나레이션 요지 / 자료 종류·출처 / 필요한 모션.
- 시각 구성: 주 소재(실제 화면·일러스트·픽토그램·큰 글자 등), 구도, 움직임이 설명할 변화, 읽는 구간, 다음 장면으로 이어지는 대상. 동일한 틀이 연속되면 이유를 확인하고 필요할 때 구성을 바꿈.
- 각 숏폼의 질문, 후크, 단일 결과, 마무리. 롱폼을 잘라 붙이는 계획으로 대체하지 않음.
- 실제로 확인한 사항과 예시로 설명할 사항, 필요한 제한 조건.

사용자가 기획을 승인하면 같은 기획의 제작·렌더에 재승인을 요구하지 않는다. 내용의 핵심 주장이나 범위를 새로 바꿔야 할 때만 해당 변경을 구체적으로 제시한다.

## 최종 검수

요청 범위에 맞는 검수만 수행한다. 전체 본편을 새로 제작했다면 전체를 검수하고, 특정 수정이라면 변경 구간과 파급 범위를 확인한다.

### 콘텐츠·시각

- 첫 3초의 주장과 화면이 일치하며 읽을 수 있는가?
- 기능 설명마다 시청자가 볼 수 있는 구체적인 결과가 있는가?
- 공식 자료·직접 실행·예시 표시가 정확한가?
- 자막 줄바꿈이 자연스럽고, 행간·자간·화면 가장자리 여백이 답답하지 않은가?
- 밝은/어두운 배경의 배색과 승인 HEX가 맞는가?
- 글자가 먼저 나온 후 밑줄·화살표·동그라미가 정확한 대상을 강조하는가?
- 캐릭터와 모션이 설명을 돕고, 읽기 시간을 침범하지 않는가?
- 선택한 스타일이 반영되었는가? 스타일 1은 실제 화면·타이포의 위계와 의미 있는 변화가 보이는가? 스타일 2는 작은 아이콘 추가에 그치지 않고 큰 그림의 움직임이 설명을 맡는가?
- 비교·과정·결과 장면이 서로 다른 크기 관계와 구도를 가지는가? 똑같은 박스 등장과 페이드 전환이 반복되지 않는가?
- 전환 중 공통 대상이나 시선의 위치가 이어지고, 핵심 문장이 잘리지 않는가?
- 세로 화면에서 제품 UI, 결과와 자막이 플랫폼 버튼 영역에 가리지 않는가?

### 오디오·동기화

- 음성 트랙이 실제로 들어 있고 승인된 목소리를 사용하는가?
- 발화 속도는 유지되고 롱폼의 의미 경계에 적절한 쉼이 있는가?
- 쉼 구간에 다음 장면·자막이 먼저 진행하지 않는가?
- 실제 발화와 자막·강조 효과가 맞는가?
- 음성 잘림·클리핑·갑작스러운 음량 변화·의도하지 않은 중복 발화가 없는가?
- 호흡 수정 중 피치·채널 구성·음량이 바뀌지 않았는가?

청취 도구가 있으면 대표 구간을 직접 확인한다. 청취하지 못했을 때 수치 검사만으로 자연스럽게 들린다고 단정하지 않는다.

### 파일

- 출력 파일의 길이·해상도·프레임레이트·영상/음성 코덱을 확인하고 전체 디코딩 오류를 검사한다.
- 설명 없이 무음이거나 검은 프레임인 구간이 없는지 확인한다. 의도된 쉼과 배경을 오류로 오인하지 않는다.
- 최종 SRT의 시작·끝·순서·영상 종료 범위를 검증한다.
- 속도나 쉼을 바꿨으면 최신 타임라인에서 SRT와 검토 자료를 다시 만든다.
- 수정 대상 밖의 승인본이 유지되었는지 확인한다.

기본 출력 예: 가로 1920×1080, 세로 1080×1920, 30fps, H.264/AAC MP4. 현재 프로젝트와 사용자 요청이 있으면 우선한다. 특정 LUFS 수치를 맞추려고 이미 승인된 음량을 임의로 바꾸지 않는다.

## 전달과 발행

- MP4, 별도 SRT, 간결한 원고·출처·예시 구분 자료를 전달한다. 대규모 문서 묶음이 아니라 실제 검토에 필요한 자료를 만든다.
- 제작·기술 검수 완료, 사용자 검토 대기, 발행 완료 상태를 구분한다.
- 사용자가 허용한 검토 후 발행 흐름을 지킨다. 공개 업로드나 예약을 할 때 대상 계정과 승인 범위가 명확해야 한다.
- 플랫폼별 설명·제목·썸네일을 준비할 수 있지만 제작 요청을 게시 권한으로 해석하지 않는다.
